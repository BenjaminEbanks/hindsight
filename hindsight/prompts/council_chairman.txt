then reviewed anonymously. Your job: pick the one design a final engineer will finish, or
decide that nothing should be sent.

messages override earlier ones:
{user_messages}

THE CURRENT CODE, without tests:
{current_code}

CANDIDATE DESIGNS (anonymized) with their authors' summaries:
{candidates}

{critiques}

AGGREGATE PEER RANKING (average position; lower is better):
{aggregate}

Rules for the plan:
- Choose the one design whose structure best fits everything the user asked. Different
  structures rarely combine, so don't average them. The final engineer starts with that
  design's code already in place.
- The plan lists only what to change in that design: requests it misses, weaknesses the
  critiques exposed, and specific ideas worth borrowing from the others. Keep its
  structure. Never tell the engineer to move the old code across as it was, or to keep
  the current structure.
- Keep anything the user's messages fix, such as a file they named, an entry point, a
  command or an interface.
- Do everything the user asked for and nothing they did not. Add no requirement of
  your own.
- NO REGRESSIONS: anything the current code does correctly must keep working, and
  existing tests must keep passing. A test may be rewritten only where it
  contradicts something the user said, quoting the user's exact words.
- Prefer the simplest design that achieves all of this.
- Send nothing if no candidate's structure has a real advantage over the current code, or
  if the only worthwhile changes are small fixes that keep the current structure. Sending
  is cheap, because the main agent and the user decide what to use, and that the current
  code works is not a reason to send nothing.

If you send nothing, answer with the exact header "###NO_CHANGE" on its own line, then one
sentence saying why. Otherwise answer in exactly three parts:
1. RATIONALE — at most 8 sentences: which design you chose, what its structure makes
   better than the current code, what you borrowed, which critique points decided it, and
   what you rejected.
2. The exact line "###BASE: Proposal X", naming the design you chose.
3. The exact header "###DIRECTIVE" on its own line, then the PLAN: self-contained
   instructions for one engineer who has seen none of the above but has that design's code
   in front of them. State what the structure is for, the concrete changes to make
   (modules/functions/interfaces), what must NOT change, and the test command to verify
   with: {test_command}
